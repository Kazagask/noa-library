# V2.1 根因分析

## 结论

当前问题不是“存档文件太大”单一原因，而是四类放大叠加：

1. **读取放大**：`session.bootstrap` 先 `repo.read` 整条世界线，再在内存过滤；`state.read(paths)` 同样先读完整 state。索引只是优化路径，未成为强制边界。
2. **上下文放大**：50 轮副本战斗、完整事件、回执与待办正文没有层次标记，默认召回会把 L3 原文当成普通记忆候选。
3. **投影漂移**：party/research/economy/pendingEvents 可从多处字段读取，缺少 `sourceRevision`、`sourceHash` 和 stale 检测；bootstrap 的队伍显示因此可能不同于权威 `actors` 状态。
4. **恢复歧义**：MCP 失败、服务端事务失败、事务成功但回执未送达、ChatGPT 表现层 SSE 中断，四种情况在客户端看起来相同，缺少轻量恢复入口来区分“已提交”与“待提交”。

物理分片 4056 个、26.39 MB 只是结果。`vault_compact` 没有可回收对象说明问题在逻辑分层和读取路径，而非单纯压缩。

## 证据链

- 生产巡检：历史事件最大约 85KB，待办最大约 99KB，单条大对象即可占满常规上下文预算。
- Checkpoint 89 个 / 7.81 MB：快照保留完整状态与记忆，缺少基准+增量与内容寻址去重策略。
- 副本战斗 50 轮：完整原文进入情景记忆后，没有 settled→summarized→archived 的强制生命周期。
- Bootstrap 队伍投影显示一星斗尊而权威状态七星斗尊：典型同义字段与无 revision 投影问题。
- SSE 中断：服务端无法也不应声称能修复 ChatGPT 客户端表现层；只能保证幂等和审计可恢复。

## V2.1.1 实测补充

真实 Worker + 隔离 D1 的 10,000 次合成 commit 耗时 53.8 分钟，扫描约 98.5 GB，说明写路径同样存在整条世界线重建/扫描放大。读取预算治理不能替代写路径增量专项。

## 不应采用的做法

- 缩短提示词或只靠 LLM 自行过滤：无法提供硬上限。
- 删除历史、补骰、重算收益：破坏审计与事实可追溯。
- 为只读冷启动另建一套权威存档：会造成第二主库。
- 增加分页参数但不改变读取路径：仍会先构造完整大对象。
